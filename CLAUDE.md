# CLAUDE.md — инструкции для Claude Code

Этот файл читается Claude Code при работе в репозитории. Он описывает правила, которые нужно соблюдать при написании и изменении кода проекта **Autism Connect MVP**.

Перед началом работы над задачей всегда сверяйся с `ARCHITECTURE.md` и `DATABASE.md` в корне репозитория — они первичны по отношению к любым предположениям.

---

## 1. Контекст проекта

Autism Connect — AAC-веб-платформа (альтернативная коммуникация) для детей с РАС. Ключевая аудитория — дети 2–10 лет и их родители. Это влияет на приоритеты кода:

- **Простота и надёжность важнее гибкости.** Экран ребёнка должен быть максимально предсказуемым.
- **Никогда не хардкодь контент** (карточки, категории, тексты расписаний) в коде компонентов или сервисов — только через БД и API. Если задача выглядит так, будто проще добавить массив с карточками в код — это неверный путь, останавливайся и используй seed/БД.
- Любая новая сущность контента (карточка, категория, шаг расписания) должна быть добавляемой через API/админку, без деплоя нового кода.

## 4. Backend (NestJS) — соглашения

### 4.1 Структура модуля

Каждый bounded-context модуль (`cards`, `children`, `schedule` и т.д.) следует слоям из `ARCHITECTURE.md`:

```
domain/          — сущности и интерфейсы репозиториев, без импортов Nest/Prisma
application/     — DTO, use-case'ы, сервис-оркестратор
infrastructure/  — Prisma-репозитории, мапперы
presentation/    — контроллеры, модуль Nest
```

Правило: **domain не импортирует ничего из infrastructure или presentation**. Если для доменной логики нужен доступ к данным — определяй интерфейс в `domain/*.repository.ts` и реализуй его в `infrastructure`.

### 4.2 Именование

- Файлы: `kebab-case.ts` (`create-card.use-case.ts`, `cards.controller.ts`).
- Классы: `PascalCase` (`CreateCardUseCase`, `CardsController`).
- DTO: суффикс `Dto` (`CreateCardDto`).
- Интерфейсы портов/репозиториев: суффикс `Repository` или `Port` (`CardRepository`, `CardGeneratorPort`).
- Enum'ы — `PascalCase`, значения — `UPPER_SNAKE_CASE`.

### 4.3 Валидация и DTO

Каждый входной DTO контроллера обязан использовать `class-validator` декораторы. Никаких `any` во входных данных. Пример:

```ts
export class CreateCardDto {
  @IsUUID()
  categoryId: string;

  @IsString()
  @MaxLength(60)
  title: string;

  @IsString()
  ttsText: string;

  @IsOptional()
  @IsHexColor()
  color?: string;
}
```

### 4.4 Prisma

- Схема — единственный файл `packages/database/prisma/schema.prisma`.
- Любое изменение схемы сопровождается миграцией: `pnpm prisma migrate dev --name <описание>`.
- Не пиши сырой SQL, если для этого есть штатные средства Prisma; если raw SQL неизбежен (сложная агрегация статистики) — выноси в отдельный, явно задокументированный метод репозитория с комментарием, зачем это нужно.
- Библиотека карточек (300+) и системные категории добавляются только через `packages/database/prisma/seed.ts`, не через ручные INSERT в коде приложения.
- Мапперы Prisma-модель → доменная сущность живут в `infrastructure/*.mapper.ts`, контроллеры и use-case'ы никогда не видят Prisma-типы напрямую.

### 4.5 Ошибки и логирование

- Все ошибки бизнес-логики — через кастомные исключения домена (`CardNotFoundException` и т.п.), которые перехватываются `GlobalExceptionFilter` и превращаются в единый формат ответа.
- Не используй `console.log` — только инжектируемый логгер.
- Не глотай ошибки молча (`catch {}` без обработки запрещён).

### 4.6 Тестирование backend

- Обязательное unit-тестовое покрытие для всех `use-cases` в модулях `cards`, `schedule`, `history`, `statistics` (это прямо указано как критичные сервисы в ТЗ, раздел 15).
- Use-case тестируется с замоканным репозиторием (интерфейсом домена), без поднятия реальной БД.
- Для контроллеров — минимум smoke-тест (e2e через `supertest`) на основной happy path.
- Файлы тестов — рядом с тестируемым файлом: `create-card.use-case.spec.ts`.

## 5. Frontend (Next.js) — соглашения

### 5.1 Компоненты

- Функциональные компоненты, TypeScript, без `any`.
- Файлы компонентов — `PascalCase.tsx` (`CardButton.tsx`), хуки — `useCamelCase.ts` (`useSentenceBuilder.ts`).
- Общие переиспользуемые UI-примитивы — только в `packages/ui`, не дублировать локально в `apps/frontend`.

### 5.2 Данные и стейт

- Весь серверный стейт (карточки, категории, история, статистика) — через **React Query** (`useQuery`/`useMutation`), с явными query-ключами по конвенции `['cards', categoryId]`.
- Клиентский эфемерный стейт (собираемое предложение, текущий выбранный ребёнок) — через **Zustand**. Не хранить в Zustand данные, дублирующие серверный кэш React Query.
- Все API-типы (`Card`, `Category`, `ScheduleItem` и т.д.) импортируются из `packages/shared`, не описываются заново во frontend.

### 5.3 Зона ребёнка (`(child)` route group)

Это самая чувствительная часть приложения. При работе над ней:

- **Не добавлять** никаких элементов навигации, ссылок на настройки, кнопок выхода — кроме явно указанных в ТЗ (карточки, категории, кнопка озвучивания, расписание).
- **Не использовать** мигающие/агрессивные анимации (запрещено разделом 8 ТЗ). Разрешены только плавные transition/fade.
- Тач-таргеты (кнопки карточек) — не менее 88×88px, разрешённые размеры зафиксированы в `packages/ui` — использовать готовые компоненты, а не описывать размеры инлайн заново.
- Высокий контраст — использовать только цветовые токены из `packages/ui/theme`, не заводить произвольные hex-цвета в компонентах.

### 5.4 Производительность

- Изображения карточек — только через `next/image` с `loading="lazy"` вне видимой области.
- Держать в уме бюджет: первая загрузка ≤ 2 сек, Lighthouse Performance ≥ 90 (раздел 15 ТЗ). Не добавлять тяжёлые клиентские библиотеки в зону `(child)` без необходимости.

### 5.5 Тестирование frontend

- React Testing Library для критичных фич: конструктор предложения (`sentence-builder`), логика отметки шагов расписания.
- Не тестировать тривиальные presentational-компоненты подробно — фокус на бизнес-логике хуков и стора.

## 6. Общие правила кодирования (frontend + backend)

1. **TypeScript strict mode включён везде** (`"strict": true` в `tsconfig.json`), `any` — запрещён, кроме явно обоснованных edge-case с комментарием `// eslint-disable-next-line` и объяснением.
2. **Никакого хардкода контента.** Если Claude Code видит соблазн добавить массив карточек/категорий/шагов расписания прямо в код компонента или сервиса — это сигнал остановиться и провести данные через API/БД/seed.
3. **Комментарии — только там, где логика не очевидна** (например, почему выбран конкретный порт/адаптер, а не более простое решение). Не комментировать очевидный код.
4. **Один PR/коммит — одна логическая задача.** Не смешивать рефактор с фичей.
5. **Конфигурация — только через `.env`**, никаких секретов в коде или в `docker-compose.yml` в открытом виде (использовать `.env` + `env_file`).
6. **Именование веток и коммитов:** conventional commits (`feat:`, `fix:`, `refactor:`, `test:`, `chore:`), ветки `feature/<module>-<short-description>`.

## 7. Что делать перед тем, как считать задачу выполненной

Перед завершением задачи Claude Code должен проверить:

- [ ] Код соответствует слоям DDD, домен не зависит от инфраструктуры.
- [ ] Нет хардкод-контента (карточки/категории/расписания) в коде приложения.
- [ ] Добавлены/обновлены Prisma-миграции, если менялась схема.
- [ ] DTO входных данных валидируются через `class-validator`.
- [ ] Для новых use-case'ов в критичных модулях (`cards`, `schedule`, `history`, `statistics`) добавлены unit-тесты.
- [ ] Зона `(child)` не нарушает UX-ограничения ТЗ (без мигающих анимаций, без лишних элементов управления, крупные тач-таргеты).
- [ ] Секреты и конфигурация — через `.env`, не закоммичены в открытом виде.
- [ ] Изменения не ломают REST-контракт без согласования (учитывая будущий переход на GraphQL, раздел 15 ТЗ).

---

## 8. Чего не делать без явного запроса пользователя

- Не менять согласованный стек (Next.js/NestJS/Prisma/Postgres/Zustand/React Query).
- Не добавлять сторонние UI-киты поверх Tailwind без запроса.
- Не реализовывать AI-функции (генерация карточек/соц. историй) в MVP — только готовить порты/интерфейсы под них (раздел 14 ТЗ, Phase 2/3 в ARCHITECTURE.md).
- Не добавлять авторизацию через Google/VK/Яндекс ID в MVP — это Phase 2 по ТЗ, в MVP только Email+JWT.
- Не удалять и не переписывать `ARCHITECTURE.md`/`DATABASE.md` — при архитектурных изменениях предлагать правку, но финальное решение и коммит правки — за пользователем.
